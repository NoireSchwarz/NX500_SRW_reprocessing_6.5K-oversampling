R11f9：当前进程只读核验与接续激活

已确认的失败
R11f8 完整备份校验通过，记录先后为 PREPARED、REFRESH_REQUESTED、FAILED。preload.log 的停止原因是 FRESH_BOOT_NOT_OBSERVED；它在建立 post 检查的 expected-phase 之前退出，随后条件未满足的 post 服务不能显示失败提示。实际原厂 rescue.target 不保证产生新的内核启动编号。此前验证把恢复流程模拟成新 boot_id，遗漏了同一次启动内恢复的分支。
用户实际看到的是 UI 消失十余分钟，重启后另等四五分钟恢复，没有看到失败提示。上述证据解释错误状态和提示缺失；不能据此断言已证明 UI 消失全部时长的具体原因。
R11f8 恢复前日志显示：原始和可见 libmmfcore 都是目标补丁文件，434176 字节，SHA256 7743dd26b06fb2e600cc65aff6ad92913b43c3f75b9493437239006b24991cd9；PID 288、启动 ticks 1251、映射基址 0xb4307000，并有新增段。磁盘文件和映射记录仍不足以证明当前内存代码和 gate 状态正确。

本版流程
1. 使用既有只读 ARM 校验器查找唯一相机进程，以 PID 加启动 ticks 绑定，校验实际映射、内存指纹和 command_enabled=0。检查当前系统不在恢复中、相机就绪且采样停止。连续三轮必须是同一进程。
2. 同一次 boot_id 可以通过；读取失败、空值、检查期间变化仍不能通过。启动未完成、录影/采样繁忙、库不匹配或进程变化记录为本次 PENDING，不改写旧 FAILED，不阻断后续新尝试。
3. 验证已知 R11f8 载荷、旧状态及服务归属和闲置状态；用专用 ARM 校验器完整读取 R11f6 和 R11f8 两份 157285888 字节原备份。完整备份不缩小、不覆盖、不删除。
4. 再连续核验三轮当前进程，且必须与最初身份相同。只创建独立 R11f9 回执目录；原有 R11f8 状态、载荷和报告保持原样。
5. 将两个已确认归属的 R11f8 开机 wants 链接保留到独立归档目录，刷新服务定义后，再验证同一进程。不存在任何 rescue、reboot、相机 stop/start 或核心库写入调用。不创建新的后台激活/恢复服务。
6. 归档本轮安装触发文件、写入 VERIFIED 回执并显示 CORE VERIFIED。未完成时保留或恢复安装触发入口，写本次原因并显示 WAITING；旧状态不会成为永久失败闩锁。

范围
RTOS 入口、event10、bit6、首末绑定、采集器、菜单以及 HEVC A/B/A 实验均保持既有版本。视频菜单仍显示 R11f HEVC A/B/A TEST。R11f9 是接续入口版本；ARM 校验器保留 R11f8 协议标识以保证字节不变。
仅当实际相机核验通过才接续；从电脑的 USB 存储连接不能代替读取相机运行进程。部署到 SD 不代表相机已经执行或验证通过。
本版不新增性能实验，不重复码率测试，也不宣称 bit6→bit2 的性能瓶颈已解决。
