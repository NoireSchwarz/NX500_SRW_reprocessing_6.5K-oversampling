R11f 安装失败调查与 R11f1 安装器修复

结论：本轮相机未成功安装 R11f。安装日志第 1351 行虽曾提交新 libmmfcore.so，但第 1354 行恢复系统分区只读失败，随后记录原厂库和旧模块回滚，第 1360 行入口确认失败。不能用“库曾提交”或“SD 文件已校验”代表安装成功。

最后安装前模块清单为 R11e（889f93c6...）；临时新清单为 R11f（41d27126...）。失败后没有新的 R11f READY／采样，最新 VIDEO_FULL_1794728019_415_1c3a4666 只是原生配置状态查询，RTOS_entered=0。无法仅凭 SD 查看回滚之后当前相机内存的版本。当前地图中的 libmmfcore.so 未显示 deleted，也不能倒推失败瞬间没有孤立映射。

最有力诱因：R11f 用 cp 保存旧库字节，再用新 inode 原子替换正在映射的库。旧库若丢失最后一个链接，仍被相机映射，就可能阻止 Linux 恢复只读。回滚时再次拷贝字节只能恢复哈希，无法重新链接原映射的实体。这与“提交成功 → remount EBUSY → 字节回滚成功 → 再次 remount EBUSY”的日志吻合。Linux 上游 sb_prepare_remount_readonly 明确检查 s_remove_count 与写入者。相机专有内核计数没有采集，故这是源码支持且已在明确的挂载模型中复现的候选原因，不宣称已在实机唯一证明；其他写入者仍是替代解释。

修复范围：为旧库创建同一 inode 的硬链接后才替换；为新库也保留硬链接，以免回滚时新库已被加载；回滚重新链接旧 inode，而非复制旧字节；核对同文件身份、哈希和安全属性；扩展事务路径冲突检查，保留所有历史别名。保留严格只读恢复要求，不能忽略 EBUSY。上次失败可能遗留 RW 时，在变更前拒绝安装并要求完整关机重启。

采集器、菜单、HEVC 门控库、RTOS、event10、bit6 和首末绑定均与 R11f 逐字节相同。不重复码率／私有内存压力测试。本包是安装修复加原 R11f A/B/A 诊断，不是 30p 性能修复。

验证：执行完整真实 shell 控制流程；主机文件、哈希、硬链接与 inode 身份为真实操作；Linux 挂载、SMACK、进程边界为显式模型。原 R11f 在新增零链接映射限制的同一模型下重现失败；修复验证安装、重复安装、卸载、旧模块回滚、提交后新库已被映射、各故障注入、保留历史路径和残留 RW 拒绝。具体数量与源码身份见 installer-tests.json、installer-followup-tests.json、r11f1-final-validation.json。原厂固件确认存在 /bin/ln，/bin/sh 指向 bash；不代表已在相机执行硬链接操作。

实机完成条件：先完整关机清除旧状态，再安装 R11f1；安装后再次完整关机开机。日志应有 recovery-r11f1-inode-retain、HEVC_GATE_INODES_RETAINED、正确的新模块清单、库提交及 INSTALL_COMPLETE，且同次会话没有后续失败。界面继续显示 R11f，实际内存入口仍由采样器冷启动校验。按 R11F1_TEST_STEPS.md 完成原定一次 120 秒正常→约四分之一普通帧编码→恢复 A/B/A，并等待保存成功再接 USB。部署回执不证明相机安装与实验通过。
