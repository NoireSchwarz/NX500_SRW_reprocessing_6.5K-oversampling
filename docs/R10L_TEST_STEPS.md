# R10l：帧阶段与 HEVC 追踪测试

此包用于 NX500 1.12 的瓶颈定位，尚未证明修复掉帧。保留现有全宽输入、3840×2160 输出、蓝边边界、USB 保护与 SRW 引擎。

安装后完整关机再开机，清除旧版本 RAM 计时代码。视频页应显示 **R10l STAGE + HEVC TRACE**。

1. 照片模式启动 **STAGE COUNTERS**，然后通过原生菜单进入视频模式。
2. 同一机位、焦距、曝光和白平衡，原生 UHD29.97 取景约 5 秒，录像约 25 秒，停止后约 5 秒。
3. 回照片模式，选择同样的 UHD29.97，应用 FULL WIDTH，再按相同时长测试。需要 DCI24 时可另录一段。
4. 回照片模式停止并保存 STAGE COUNTERS，看到保存成功后再连接 USB。
5. 提供这轮 `VIDEO_STAGE_*` 目录中的 `counts.bin`、`frame-flow.bin`、`hevc-flow.bin`、`DONE`，以及对应 MP4 和安装日志。

建议本轮先完成一组原生 UHD／全宽 UHD；不要把多轮操作堆在一个很长的记录里。保持两段实际目标码率相同：现有应用全宽步骤设置 80Mbps，如做 70Mbps 对照，应通过已验证的 rate70 操作恢复并核对实际参数。

## 本轮新增观测

- RTOS 仍只使用原先独占的 280 字节计数设施，没有新增图像缓冲、RTOS 堆或 SMA。每条记录保留提交、IPC DMA bit20 观察、CS0 完成观察、EP DMA 候选事件、主输出 bank0 Y 地址和原始 EP D0/D4 合并状态。
- 计时环容量为 7 帧，Linux 每 100ms 单独读取。重配置快照保持 200／500／1000ms 自适应；达到 CPU 预算后会明确停止有效覆盖，不会把快读环一起静默降为 500ms。Linux 总 RAM 缓冲约 11.03MiB。
- 原生唯一 `videoencoder` 线程使用五个硬件执行断点，观测提交前、等待返回、取结果并解锁后、编码输入端归还前后。3 秒关闭／3 秒开启交替；记录每次实际暂停的时间。原厂 ARM 内核的单步过程属于观察开销，时间不能当作纯编码硬件耗时。
- 机上必须支持至少五个可用执行断点。资源、版本、线程身份、读取或单步不满足要求时停止该部分，并在 `hevc-flow.bin` 中记录不支持／失败状态，不改用持久软件断点或应用文本补丁。帧环采集仍可保存。
- 热采样不写 SD。三个二进制文件全部在停止录像且 USB 断开后保存；部分导出失败时保留 RAM，断开 USB、回空闲后再次停止保存可重试。

## 分析

```powershell
python PC/video-stage-counters/analyze_r10l.py NXDEMO51/VIDEO_STAGE_xxx --out analysis.json
```

`frame-flow.bin` 是本轮帧级覆盖的主要证据。`counts.bin` 的重采样仍可能跳过计时环条目，应同时看快速流的最大间隔、覆盖标志和序号缺口。

EP D0/D4 记录属于活动 IPC 窗口中的 DMA 观察，尚未由原厂消费者证明是 WDMA2 完成，也尚未获得独立 EP 作业标识。地址变化会明确标记，不能直接把 EP 中断数当作帧数。

Linux CLOCK_MONOTONIC 与 RTOS 26MHz 是不同的时钟域。分析器分别输出各段耗时，仅列出地址与主机观察窗口一致的关联候选，不直接相减两种时钟、不强行宣称跨域原生帧号已经证明，也不自动归因于 DDR。

HEVC 的输入端归还返回只表示对应原厂调用返回，不代表所有 DMA 或其它引用已经退役。先比较跟踪开／关窗口内的帧耗时，确认观察扰动，再判断访存或反压。

本地验证覆盖真实 ARM 指令与受控 OS／外设模型。真实相机吞吐、断点可用性和画面质量仍需本轮机测确认。
