# R10y：录像期内存与跨请求缓冲观测

这是Linux端观测升级。保持相机已测R10x所用RTOS、全宽helper、event10、bit6、首末输入绑定逐字节不变；不新增RTOS分配、执行断点、ptrace、fork、IRQ/ACK、调试选择器或缓存同步操作。不能以离线模型通过宣布实机帧率已修复。

## 实现

`video_buffer_capture.h` 新增独立的 `NXL_BUFFER_MEMORY1` 导出，文件为 `buffer-flow.bin`。原有三个文件的格式不变；`analyze_r10y.py` 合并四文件并继续读取历史三文件捕获。R10y缺少第四文件时解析拒绝完整分析。旧R10x的FAST mask0xe仍是缺读，不会由新白名单追认为完整。

生产 `physical_allowed` 补回0x2081040c的4字节只读访问；新增4096字节读取仅限RTOS分配表0x81dfc908..+720896，保留原有标量RAM读取。IRQ ACK0x20810440、EP ACK0x20821050等仍拒绝；没有扩大MMIO窗口。Linux进程只读块上限改为4096，用于按已验证类型/容量读取MMF槽表。

采样RAM文件为18,560,000字节，比前版增加6,799,488字节（约6.48MiB，Linux侧）。这不是进程全部内存；栈、程序及页映射另计。新增前检查tmpfs剩余容量；空间不足在READY前拒绝，保留已有记录。RTOS堆、CAP图像池和硬件分配新增为0。

重快照从500ms开始，保留500/1000/2000/5000ms退让；旧富字段PIPELINE2快照降为冷读（初始5秒一次），不再调用旧的同请求密集循环。100ms FAST4环读不变。

新的轻量窗口默认每10秒尝试一次，持续至最多36向量、500ms、约8ms CPU预算或录像生命周期改变。每向量请求间隔4ms，允许跨多个原生请求，每100ms切片主动让出下一次环读取。读前/读后完整原生头、驱动/预设、WDMA2配置、Linux源/HAL/Buffer类型与结构身份分别检查。CPU限额是停止继续读取的软预算，单次向量/内核访问可超出，实际CPU和墙钟时长保留；不伪报固定4ms分辨率。

完成pending只在同请求原生头、CS0状态bit2、enable和真实bit2回调都吻合后允许最多两次补读。第一次读到新请求时只保存拒绝的初始头，不继续该次补读的DMA/对象读取。相同请求不会重复重新武装两次补读。常规轻量窗口可以继续跨请求，不能将它与同请求pending补读混为一谈。

## 原厂类型与生命周期

新增四个32字节原厂ROM守卫覆盖Buffer构造/两组地址getter和CImage构造。libmmfcore.so、libmmfmodules.so仍通过已有完整库哈希核验。CImage的Buffer从+0x68开始，类型及两组地址整体保存，两次类型/内容一致才解释。类型0是top地址；2 RAW；3 RGB；5平面Y/Cb/Cr；6 Y0/Y1/C0/C1；7 Y/Cbr。两个数组各自有原厂含义，不能将+0x6c零值或+0x7c非零值直接叫作物理输出地址；与实际DMA地址对照后也只形成地址域候选。

HEVC保存原厂stAddrEnc全部32字节，而非前16字节。+0x174仍只表示取结果路径进度，不宣称成功编码或输入缓冲释放。

编码器输入Buffer必须通过当前源、编码器类型、端口和Buffer类型核验。R10x真实稳定录像161份样本的编码输入类型均为cMmfBufferQue，输入对象0x780e78，容量64；不是普通Buffer。原厂cMmfBuffer槽为0x78字节、状态+0x70、FrameData+0x10；cMmfBufferYuv槽为0x70字节、状态+0x68。实际Que类型另按原厂布局读取：对象+0x1c容量、+0x20槽数组；槽0x70字节、FrameData+8、状态+0x68，+4持有64字节元数据副本的所有权指针。未知类型不猜偏移。全部槽状态压缩保存，优先选取处理中的槽，其次选已满槽，跨请求跟随FrameData与64字节YUV描述。Buffer类型、数组位置、容量变化均拒绝关联，保留原始头和失败阶段；不读取图像像素。

原厂ARM确认SetBufferFull 1→2、GetFullBuffer 2→3、SetBufferFree 3→0。Que还支持取消预留的1→0；GetFreeBuffer为0→1并申请/清零元数据副本。Que归还会delete槽+4的元数据，清除+4/+8/+c/+60，再置状态0；本采集器不会调用这些函数，也不会在归还后解引用已清除的指针。归还候选使用已观察的处理状态、归还清零形态和保留的FrameData字段进行关联。它仍不证明物理图像的所有消费者已退役，也不能绝对排除未观察的ABA。WDMA2地址与后续请求HEVC地址一致只报告跨请求候选，不自动宣称精确图像代次或硬件完成时间。

池读取失败阶段：1编码器/根缺失；2端口不匹配；3头读取失败；4类型不支持；5容量/范围非法；6前后布局变化；7槽表读取失败；8非法状态；0成功。未尝试为0xffffffff。

## 四阶段内存快照

全宽录像前取景、录像前段、录像约30秒后的后段、停录后取景，各最多一份尝试。一次尝试包含三次原厂分配器头、两份完整分配表、两组136项已验证只读DMA配置及逐项读取掩码；另在快照首末保存经过类型核验的Linux源/HEVC描述符和原生头，将HEVC输入Y/UV纳入同一物理分配引用统计。分配表每份720896字节，每100ms空余切片至多16个4KiB块、约0.5ms CPU；不在每次快读复制整表。分配表、路由均分阶段执行，25秒超时、模式变化、读失败、停止未完成分别保留。

表头状态：1读取中；2读取完成；3模式/对象改变；4读取失败；5停止时未完成；6超时。最终阶段与游标记录读到了哪里。两份原始表和哈希保留，完整分区不合法时拒绝容量结论。原厂aggregate free可能失真，只用于原始证据，不当成可分配容量或主动修复。

解析按物理分配区间将IPC/EP各路已读Y/UV地址映射到包含它们的分配，跨路引用按物理区间去重。报告“引用到的分配区间”，不称为精确活跃图像字节数或DDR流量。缺失长度、未知所有者和未落入分配表的地址分别标记。CAP逻辑bank不等于物理DDR通道。

新映射或两次相同的Linux可见内存不证明RTOS脏缓存已经发布。格式明确保留 `RTOS_cache_publication_proven=false`、`live_allocatable_capacity_proven=false`。需要将分配区间、实际DMA/对象地址和原厂缓存契约结合判断，不能为求一致而主动暂停RTOS、锁分配器、试分配大块内存或发送缓存同步。

## 保存与验证

停止、相机/USB退出后仍使用原有RAM保留与闲时保存流程。新增文件逐记录检查、表副本哈希检查、原子临时文件重命名和已有文件逐字节比较；四文件全部成功后才发布DONE。第四文件冲突/同步失败不会显示保存成功，可在保留RAM后重试。

保存文件绑定同一cookie、进程身份、相机启动身份及起始时间；分配表既保留读入前缀哈希，也在闲时导出时计算整个副本哈希，未读取的尾部同样受完整性保护。

验证包含：真实生产ARM白名单与FAST组合；新观测器17场景及错误证据拒绝，含Que归还/类型变化/ABA/元数据读取失败；原厂Buffer getter和三种MMF槽生命周期54场景，含Que元数据申请和释放；132秒生产采集器模型使用实际Que布局，检查四阶段内存/100ms覆盖及不读取已释放的元数据；空间不足和第四文件故障恢复；既有观测、启动/停止菜单协议及15份历史捕获回归。模拟OS、MMIO、内存、缓存可见性和时间端点不等于相机硬件测量。RTOS/全宽事务验证按精确哈希引用既有报告，不重新运行生成脚本。

验收仍是识别普通帧约8.22ms、总体约9.23ms缺口中可消除的等待或冗余；不靠更多空闲内存、连续PTS或补帧宣布真30p。
